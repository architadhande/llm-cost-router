# Learning Log

## Session 1 — Phase 0: Hello, models (2026-11-12)

**Concepts covered**
- **API keys in `.env`:** keys live in a file that is gitignored and loaded with python-dotenv, so they never end up in code or on GitHub.
- **Retries with exponential backoff:** temporary server errors (429 rate limit, 503 overloaded, 504 timeout) are worth retrying after waiting 2s, 4s, 8s… Client errors like 401 (bad key) or 400 (bad request) are permanent, so retrying just wastes time.
- **Token usage:** each response reports input tokens, output tokens and reasoning ("thinking") tokens. Reasoning tokens are billed as output, so a "short" answer can still cost a lot. Gemini used 523 of its 585 output tokens on thinking.
- **Latency varies a lot:** Groq answered in ~0.5s; Gemini took ~8s after two 504 retries.
- **Python debugging:** `NameError` means using a name that was never defined. A file edit only counts once it's saved to the path the program actually reads.

**Interview answer**
> "Every API call in my project goes through a retry wrapper with exponential backoff. It retries transient failures like 429s and 5xx errors but fails fast on other 4xx errors, because those mean the request itself is wrong. On day one Gemini returned 503 'high demand' several times in a row, and the wrapper is what kept that from crashing the pipeline."

## Session 2 — Phase 1: Collecting prompts (2026-11-12 to 11-14)

**Concepts covered**
- **A classifier only learns what it sees:** the router needs a mix of easy and hard prompts, or it can't learn what "needs the frontier model" looks like.
- **Stratified sampling:** take an equal number from each category (150 per Dolly category) so the common types don't swamp the rare ones, and the overall score can't hide a weak category.
- **Reproducibility:** a fixed `random_state` gives the same sample every run, so the data can be rebuilt from code (which is why `data/` is gitignored).
- **Prompts need their context:** some Dolly tasks refer to a passage in a separate column. Sending the instruction alone would produce bad labels.
- **Ground truth vs. judge:** GSM8K's `#### <number>` gives an exact `final_answer`, which can be used to check the LLM judge itself.
- **Controlled templates:** the same 4 tasks on every business snippet, so differences in difficulty come from the task, not the text.
- **Caching API calls:** search results saved after every call, so re-runs cost 0 credits and a crash loses nothing.
- **Stable content-hash IDs:** `prompt_id` = hash of the prompt text, so the same prompt always gets the same ID. It also caught duplicates that URL-based dedup missed.

**Dataset:** 2,178 prompts = 1,198 Dolly + 400 GSM8K + 580 business (Tavily/Exa).

**Interview answer**
> "I built a 2,178-prompt dataset from three public sources with very different difficulty: general instructions, multi-step math with exact answers, and business tasks I generated by applying four fixed templates to real web snippets. I stratified the samples, kept a ground-truth answer where one existed so I could validate the LLM judge, and gave every prompt a content-hash ID that also serves as the cache key, so no prompt is ever paid for twice."

## Session 3 — Phase 2: Labelling under free-tier limits (2026-11-15 to 11-19)

**Concepts covered**
- **Quotas shape the design:** Groq caps gpt-oss-120b at 200K tokens/day (~350–400 prompts), and Gemini 3.8 Flash at 20 requests/day, often returning 503/504 overloaded errors. Hence a 910-prompt sample, 10 prompts per judge call, and a resumable cache-backed loop that runs every 2 hours.
- **Truncation is a silent label bug:** at 400 max tokens, 32% of answers were cut off, so a "fail" meant "ran out of room", not "too hard". A concise system prompt brought that to 0% with 1,000 tokens.
- **LLM-as-judge design:** blinded (no model names), shuffled, pointwise pass/fail, with a human reference answer when one exists. The judge writes its evidence lists (unsupported claims, factual errors) *before* the verdict, which made it stricter.
- **Validate the judge:** the cheaper Lite judge passed 32/32 answers, including 3 clear errors I checked by hand, so it was rejected. 96 blinded hand labels measure how often the judge agrees with a human.
- **Exact-match where possible:** GSM8K uses `grade_gsm8k` (last number in the answer vs. `####`), not the judge.
- **Round-robin ordering:** the work is ordered one prompt per category in turn, so if a run stops partway, every category is still covered evenly.

**Interview answer**
> "Labels were the expensive part. I graded answers with a different model family as the judge, blinded and shuffled, and forced it to list evidence before giving a verdict. I also validated it: a cheaper judge model looked fine but passed answers with errors I had verified by hand, so I rejected it. Everything is cached by prompt hash and runs in a resumable loop sized to the free-tier quotas, so the whole labelling run cost $0."

## Session 4 — Phases 3–6: Router, evaluation, write-up (2026-11-20 to 11-21)

**Concepts covered**
- **Out-of-fold scoring:** every prompt is scored by a model that never saw it in training (5-fold CV). That lets all 350 labels serve as both training and test data, honestly.
- **ROC-AUC vs. PR-AUC:** ROC-AUC 0.5 is a coin flip. PR-AUC is measured against the positive rate (31%), so it shows how well we find the rare "needs frontier" prompts.
- **Cost per successful outcome:** total cost ÷ number of passing answers. It punishes a cheap model that fails often, which "tokens saved" never does.
- **Baselines frame the result:** always-cheap, always-frontier and the oracle (a perfect router). With only a 2× price gap, always-cheap wins. Routing only pays at bigger gaps (40–54% savings at 10×).
- **Choose the target carefully:** "cheap fails" includes prompts the frontier model fails too. "Frontier rescues it" is the better target, but with 43 positives it was too sparse to learn yet.
- **Judge agreement:** an independent second grader agreed with the judge 82% of the time. Disagreements cluster in long, detail-heavy answers.

**Interview answer**
> "My router beat a simple rule (ROC-AUC 0.62 vs. 0.54), but the honest headline was economic. With the frontier model only 2× the price, always using the cheap model gave the best cost per success. Routing only pays when the price gap is large. I also found most cheap-model failures were frontier failures too, so the right target is 'the big model would fix this'. That needs more labels, which is exactly what I'd collect next."
